## 1. 目标与决策

Envoi 的插件定位是「研究工作区的能力包」，服务于阅读、写作、运行实验和使用远程机器。插件的价值既包括编辑代码，也包括逐步打通「运行实验 → 保留结果 → 用于论文」的流程。

Envoi 建立自己的轻量插件机制，第一阶段只加载随应用发布、由官方维护的插件。用户在统一的「扩展」页面管理语言支持、远程连接和主题。界面以用户能完成的事情组织能力，底层语言服务器作为插件详情中的工具选择。

核心决策：

- 复用 clangd、rust-analyzer、Python 语言服务器、CMake 等现成工具；Envoi 实现工具适配和交互。
- 插件通过统一注册接口提供能力，不再依靠核心代码中不断增加语言和工具分支。
- 官方插件代码随 Envoi 更新；外部工具独立管理，优先复用用户已有安装。
- 从第一阶段区分本地界面和工作区执行环境，语言插件能在本地与 SSH 工作区复用。
- 主题采用声明式资源包。其他编辑器主题的导入转换是后续能力。
- 核心统一拥有任务执行状态和实验结果记录；插件提供运行方式及产物线索，避免各语言形成互不相通的结果管理。
- 首版接口以迁移现有能力为依据，先完成 C/C++ 样板，再用 Python 和 Rust 验证通用性；按真实需求扩展框架。

第一阶段不包含 VS Code/Zed 可执行插件兼容、公开插件市场、第三方任意代码加载、独立插件热更新、通用调试器框架，也不要求每个语言插件达到完整 IDE 的功能范围。

“内置插件”与“内置工具二进制”分开：插件可随应用提供，语言服务器仍可按需安装。启用插件不代表已经安装编译器、解释器或构建工具链。

### 1.1 扩展分类与粒度

判断是否独立成插件的依据是：用户是否会独立选择、配置或停用这项能力。补全、诊断、文件识别等公共机制由核心提供，具体语言和工具贡献对应适配。

| 类型           | 能力包                                                | 核心职责                             |
| -------------- | ----------------------------------------------------- | ------------------------------------ |
| 语言与工具扩展 | C/C++、Python、Rust、CMake；未来可迁移 LaTeX 工具适配 | 编辑器、诊断、任务执行与输出展示     |
| 工作区连接扩展 | Remote SSH；其他环境按需求增加                        | 文件身份、保存、进程、终端与断线恢复 |
| 声明式资源扩展 | 主题；未来可增加论文模板                              | 资源校验、展示、应用与回退           |

三类扩展共用身份、配置和管理入口，但按各自需要管理生命周期：语言服务按工作区运行，连接扩展承载工作区环境，主题按界面加载数据。未来模板和 LaTeX 适配的拆分不作为首版前置条件，现有论文编辑与编译继续可用。

### 1.2 目标用户流程

第一步让用户在语言扩展中看清实际运行环境、所选工具和服务状态。例如启用 Python 后，可以选择解释器与虚拟环境，确认补全和诊断是否运行；后续再通过统一任务入口运行脚本并查看输出。

完整研究流程的目标是：在远程 Python 工作区运行实验，查看输出，选择生成的 CSV 和图片保存为实验结果，再在论文工作区使用图片，并能回到对应的实验记录。任务与结果接入属于后续阶段，当前草案不将其标记为已实现。

## 3. 第一批插件

| 插件 ID（拟定）    | 用户名称   | 运行侧                | 首批职责                                      |
| ------------------ | ---------- | --------------------- | --------------------------------------------- |
| `envoi.remote-ssh` | Remote SSH | 本地连接管理          | SSH 主机连接、远端服务引导、工作区与终端接入  |
| `envoi.cpp`        | C/C++      | 本地声明 + 工作区工具 | C/C++ 文件识别、clangd 适配、服务器配置及状态 |
| `envoi.rust`       | Rust       | 本地声明 + 工作区工具 | rust-analyzer 适配、Cargo 项目识别            |
| `envoi.python`     | Python     | 本地声明 + 工作区工具 | 解释器/虚拟环境选择、语言服务器适配           |
| `envoi.themes`     | 内置主题   | 本地界面              | 现有主题、主题选择和默认回退                  |

clangd 在内部是独立的工具提供者，在用户界面归属于 C/C++ 插件，不要求用户同时启用两个插件。保留现有 ccls 等后端选择，迁移期间不静默替换用户配置。

CMake 为后续独立插件 `envoi.cmake`，分开提供 CMake 文件语言服务与配置、构建、测试能力。CMake 项目可以跨语言，不把它作为 C/C++ 的强制依赖。

Make、Meson、TOML 及现有其他工具在迁移期间由内置兼容模块继续注册，不因首批插件名单而消失。后续再决定拆分粒度。

### 3.1 分阶段能力边界

- C/C++：先保持现有补全、诊断、悬停、定义跳转；再接入 clang-format 和编译数据库诊断。clangd 可用不代表编译器可用。
- Rust：先迁移 rust-analyzer；后续增加 Cargo 构建/测试与 rustfmt 命令。发现 `Cargo.toml` 不自动执行构建。
- Python：先保留现有语言服务器选择和项目虚拟环境优先规则，提供明确的解释器选择。解释器与语言服务器分别记录，切换解释器后重新配置或重启服务。
- CMake：编辑支持与构建支持分别显示状态；后续通过 Presets、CLI、File API 获取配置和目标，按生成器能力使用 `compile_commands.json`，不假定所有生成器都能产生它。

## 4. 架构

```text
Envoi 界面
  编辑器 / 文件树 / 扩展页面 / 设置 / 主题
                  │
Envoi 核心服务
  插件注册与生命周期 / 命令与设置 / LSP 客户端
  工作区管理 / 工具管理 / 日志与状态
                  │
          WorkspaceEnvironment
           ┌──────┴──────┐
       Local 环境       SSH 环境
       本地文件服务     SSH 通道
       本地进程服务       │
                    远端 Envoi Agent
                    文件 / 进程 / 终端
           │             │
       clangd / rust-analyzer / Python LSP / 构建工具
```

### 4.1 核心职责

核心提供注册、生命周期、编辑器交互和执行基础设施；插件只提供具体能力的声明及必要适配。

核心统一管理：

- 文件类型、语言服务、工具、命令、设置和主题的注册与冲突检查。
- 工作区环境身份、文件访问、进程启动、取消、终端与文件监听。
- LSP 协议、文档版本、会话隔离、诊断发布及 UI 展示。
- 工具安装、检测、版本选择和失败恢复。
- 插件状态、日志、错误提示与资源释放。
- 后续统一任务的运行记录、输出和取消，以及实验结果的持久化、来源关联与跨工作区使用。

Remote SSH 插件负责连接、部署和提供环境适配；连接建立后，由核心通过同一个工作区环境访问远端文件、进程与终端。文件树、Git、编译器和语言服务不得各自另建 SSH 执行通路。

第一版只加载构建时列出的官方模块，不扫描任意目录执行代码。官方适配代码运行在受控的主进程服务边界；工具运行于独立子进程。此方案提供接口约束和故障处理，不宣称对官方插件代码实现了安全沙箱。

### 4.2 插件结构

建议目录，实际命名可在实现时按仓库结构调整：

```text
app/plugins/
  cpp/manifest.json + index.mjs
  rust/manifest.json + index.mjs
  python/manifest.json + index.mjs
  remote-ssh/manifest.json + index.mjs
  themes/manifest.json + themes/*.json
```

Manifest 至少声明：

| 字段                               | 含义                                                                         |
| ---------------------------------- | ---------------------------------------------------------------------------- |
| `id`、`version`、`apiVersion`      | 稳定身份、插件版本、核心接口版本                                             |
| `displayNameKey`、`descriptionKey` | 国际化文案键                                                                 |
| `activationEvents`                 | 按类型声明有限的激活条件，如文件语言匹配、用户命令或连接操作；纯资源包可省略 |
| `contributes`                      | languages、tools、languageServers、commands、settings、themes                |
| `capabilities`                     | 说明需要的文件、进程、网络或连接能力，不表示已提供权限隔离                   |

注册时检查重复 ID、重复贡献、未知贡献类型和不兼容 API 版本。主题等纯资源包不要求执行入口。

首版使用官方固定注册表和有限激活条件，不实现复杂激活表达式、通用插件依赖解析或公开 SDK。外部工具需求通过工具贡献声明；若后续出现真实的插件间依赖，再引入 `dependencies`，同时补齐缺失依赖、版本约束与依赖环检查。任务与结果贡献在对应阶段定义，不预先冻结接口。

能力声明供核心检查和用户理解使用，不等同于操作系统级权限隔离。新增第三方执行代码前必须另行设计隔离机制。

### 4.3 生命周期

有执行入口的插件按作用域管理代码状态：`registered → inactive → activating → active`，失败进入 `failed`，停用后进入 `disabled`。可通过用户重试从 `failed` 恢复。语言插件的激活上下文按工作区隔离；连接插件另外管理连接会话。纯资源包只管理注册、校验、应用与卸载，不创建工作区进程或套用执行插件的激活流程。

工具状态单独记录：未检测、缺失、安装中、可用、不兼容、启动失败。插件启用且工具缺失时，普通编辑仍可用，语言服务显示缺失原因。

每次激活得到独立上下文和可释放注册句柄。激活中途失败时释放已经创建的资源；停用、关闭工作区和应用退出时停止对应进程、监听与订阅。失效会话的诊断不可继续写入编辑器。

插件启用状态支持全局默认及工作区覆盖。停用语言插件保留文本编辑和基础高亮；停用正在承载工作区的 Remote SSH 时，先处理未保存内容，再关闭远程工作区。停用当前主题包前先切换到核心内置的最小回退主题。

## 5. 工作区执行环境

### 5.1 统一接口

所有需要访问项目或执行工具的插件通过工作区环境操作。以下为接口职责，尚非稳定 SDK：

| 接口              | 要求                                                                 |
| ----------------- | -------------------------------------------------------------------- |
| `identity`        | 环境 ID、连接代次、操作系统、架构和能力集合                          |
| `fs`              | 读取、写入、列目录、元信息、监听；明确错误和取消语义                 |
| `process.spawn`   | 可执行文件、参数数组、工作目录、环境变量、输入输出流、退出状态和取消 |
| `terminal.create` | 在环境中创建 PTY；与非交互工具进程分开                               |
| `tools.resolve`   | 在该环境内解析工具位置和版本                                         |
| `paths`           | 由目标环境解析路径、规范化和生成 URI                                 |

不把远程 POSIX 路径交给本地 Windows 路径函数处理。文件身份包含环境与工作区；同名路径在不同主机上不能共享文档、缓存或 LSP 会话。

LSP 服务器看到目标环境的文件 URI；Envoi 内部保留环境限定的文档标识，在边界转换。会话至少按窗口所有者、环境、工作区、语言和服务器隔离，文档订阅继续按编辑器实例和版本管理。

项目外的系统头文件等跳转目标通过单独的只读访问能力处理，不通过扩大项目写入边界解决。沿用现有路径验证，并在实际执行环境中处理规范路径与符号链接。

### 5.2 配置优先级

一般配置按「工作区覆盖 → 环境覆盖 → 用户全局 → 插件默认」解析，并在详情页显示来源。

可执行文件绝对路径、解释器位置等与机器绑定的设置必须限定环境。全局本地路径不可自动带到 SSH 主机；允许跨环境继承的只有明确标记为可移植的设置，例如逻辑服务器选择。

项目文件可以声明可移植偏好；安装路径、SSH 凭据和主机个人设置保存在用户侧。项目提供的命令、服务器路径或环境变量属于可执行配置，必须通过工作区信任策略后才能使用。

## 6. Remote SSH

### 6.1 首版支持边界

建议首版支持桌面客户端连接 Linux x86_64 主机；具体发行版和运行时最低版本在开发前由 Agent 打包验证确定。macOS、Windows 远端及其他架构后续扩展，不默认为支持。

第一版复用系统 OpenSSH 的配置与认证能力，优先支持已有 SSH 配置别名、密钥及 ssh-agent。需要交互认证但当前连接流程无法处理时明确提示，不把密码收集作为隐式备用方案。跳板机等配置只有端到端验证后才列入支持矩阵。

### 6.2 连接流程

1. 用户选择或输入主机配置，启动 SSH 连接。
2. 使用 OpenSSH 主机密钥校验；首次信任明确展示，密钥变化停止连接，不自动绕过。
3. 探测远端系统、架构、运行时和已有 Agent 版本。
4. 首次部署前展示将创建的用户目录和组件；用户打开远程工作区的流程中确认安装。
5. 将匹配平台的 Agent 安装到专用版本目录，例如 `~/.envoi-server/<version>/`；核对完整性后原子切换到可运行版本。
6. 通过 SSH 通道启动 Agent，握手协商协议、能力和会话身份。
7. 用户选择远端目录，创建远程工作区，随后按需激活语言插件。

Agent 包必须包含或明确声明所需运行时，不能假设远端预装 Node。第一版倾向由本地客户端下载并经 SSH 上传，减少对远端公网访问的依赖。完整性校验基于随可信发行提供的清单。

### 6.3 通信与兼容

Agent 经 SSH 标准输入输出承载有长度边界、请求 ID 和大小限制的 RPC；日志走独立通道，不混入协议流。文件数据、进程流和终端消息需要分块、流量控制、超时与取消。

第一版不在远端暴露公网监听端口。插件逻辑及 LSP 客户端主要由本地核心编排，远端 Agent 提供文件、进程和终端服务，不另建一套可动态安装插件的远端市场。

Agent 使用与客户端匹配的协议主版本；不兼容时禁止建立工作区并提供安装匹配版本入口。不同客户端版本可保留各自 Agent 目录，不覆盖正在使用的实例。

### 6.4 断线与恢复

- 断线时标记文件内容可能过期，停止提交写操作，保留本地未保存缓冲区。
- 不自动重放构建命令、终端输入或结果不确定的写操作。
- 重连创建新的连接代次，使旧响应失效；重新获取文件版本并检测冲突，再允许保存。
- LSP 会话重新启动并同步当前编辑缓冲区；终端首版允许标记已断开后重建，不承诺持久会话。
- Agent 通过会话租约与子进程归属追踪清理失联资源；只处理 Envoi 所有的进程，不终止用户的其他任务。

远程文件写入需要版本前置条件和可查询的操作结果；连接中断后通过读取状态确认结果，不把“请求已发出”当作保存成功。

## 7. 工具安装与更新

解析顺序：用户在当前环境显式指定的位置 → 插件定义的项目环境位置 → Envoi 管理的已选版本 → 当前环境 PATH。Python 项目虚拟环境继续作为项目环境候选；显式选择优先。

迁移时保留现有工具选择和成功解析的位置，安装新版本不会静默切换正在运行的服务。

首版先支持发现和配置已有工具。自动安装采用逐工具提供者实现，不承诺所有工具都可一键安装：

- 下载前明确工具名称、版本、来源、大小（可获取时）及目标环境。
- 只使用登记的官方来源和支持的平台构建，校验摘要；来源或完整性不可验证时停止自动安装。
- 安装进入暂存目录，探测成功后原子发布；失败保留原有可用版本。
- 外部包管理器安装与可独立下载的二进制采用不同流程，避免隐式全局升级。
- 工具日志限制体积并去除凭据；安装记录包含来源、版本、摘要和许可证信息。
- 管理操作只删除 Envoi 管理目录中的明确版本，不删除 PATH 中的用户安装。

## 8. 主题插件

统一主题资源包含：稳定 ID、名称、明暗类型、界面语义颜色、编辑器语法颜色、阅读内容颜色及状态颜色。

第一批迁移 graphite、classic、midnight、forest、paper、mist，保留现有选择及强调色偏好。主题必须覆盖编辑器、Markdown、聊天、表格、文件树、弹窗和通知等实际界面。

核心负责校验主题字段并映射至 CSS 变量和高亮样式；缺失字段采用完整默认主题补齐，无效颜色报告错误。资源包只接受定义好的颜色和样式值，不注入任意 CSS、脚本或外部资源。

核心保留一个不可移除的最小回退主题，避免主题包禁用或加载失败导致界面不可读。字体和字号仍按现有个人偏好独立设置，不被主题包强行覆盖。

后续可增加 VS Code/Zed 主题导入器，将静态资源转换为 Envoi 格式，并报告不支持的字段。语法标签体系不同，不承诺逐项还原；首版不为导入主题执行源插件代码。

## 9. 扩展页面

最小扩展页面随首个 C/C++ 插件一起交付，提供内置扩展列表、详情、启用范围、工具配置、状态和日志入口；随着插件数量增加，再完善搜索和分类。不展示尚不存在的社区市场，也不等待主题迁移完成才提供管理入口。

每个插件显示名称、说明、启用状态、插件版本、实际运行位置和能力状态。详情页包含：

- 全局或当前工作区启用开关，以及当前生效范围。
- 工具路径、版本、配置来源和检测结果。
- 当前环境标签，例如「本机」或「SSH: research」。
- 安装或配置工具、重试、重启语言服务、查看日志的入口。
- 插件相关设置和有实际支持的命令。

状态文案区分「已启用」「缺少 clangd」「正在启动」「运行中」「连接已断开」与「启动失败」。不把“找到可执行文件”显示成“语言服务运行正常”。

用户打开 C++ 文件但缺少 clangd 时，仍可编辑，并在状态入口展示配置操作；只有该工具的自动安装已经支持时才显示安装入口。安装应在当前工作区所在环境执行；远程工作区不能误装到本机。

### 9.1 后续任务与结果接入

语言和工具扩展可贡献运行方式，例如 Python 脚本、Cargo 测试和 CMake 构建；核心统一展示任务入口、运行状态和输出。任务需明确参数、工作目录、目标环境、取消语义及退出状态，复用工作区信任和进程服务。识别到项目文件不自动执行任务。

任务结束后，插件可提供产物候选，由用户选择需要保留的图片、表格或日志。核心负责结果记录的数据结构与持久化，并在实现前核对和复用现有实验结果机制。结果记录关联本次运行的命令、目标环境、退出状态，以及可获得的代码版本和工作区修改状态；无法获取的信息标记为未知，不能据此宣称实验可完整复现。记录中不保存凭据或未经筛选的环境变量。

保存结果时必须区分远端文件引用与已经保留的产物副本。供论文工作区使用的副本需完成传输并验证内容一致性后才标记可用；保留来源记录，避免远端路径失效后仍显示为已保存。失败或中断任务的产物可以显式保留，但应保留其真实任务状态。

验收流程包含：运行脚本 → 查看输出 → 选择 CSV/图片 → 保存结果 → 在论文工作区使用 → 回到来源记录。此流程在阶段 D 实现，不要求阶段 A 提前建设通用工作流引擎。

## 10. 实施顺序与验收

### 阶段 A：C/C++ 完整样板与最小扩展页面

建立官方固定注册表、最小 Manifest 校验、按工作区激活与释放机制，以及满足现有能力的 Local 环境接口。迁移 C/C++ 的文件识别、工具声明和语言服务配置，同时交付扩展列表、详情、启停、状态、配置及日志入口。

验收：C/C++ 现有补全、诊断、悬停与跳转不退化；启停不会留下进程或过期诊断；用户已有路径和服务器选择仍生效。界面能区分停用、缺失工具、启动中、运行中和失败，并支持恢复。未迁移语言和工具通过兼容模块继续可用。

### 阶段 B：Python 与 Rust 验证通用接口

优先迁移 Python，用解释器、虚拟环境和独立语言服务器的配置关系检验接口，再迁移 Rust。按真实差异补充适配点，完善配置来源和运行环境展示。

验收：保留已有语言服务器选择和虚拟环境优先规则；切换解释器后服务使用正确配置；工作区间配置和会话隔离。新增测试语言声明无需在 LSP 核心增加具体语言分支，Rust 的现有语言能力不退化。

### 阶段 C：Remote SSH 最小闭环

完成 SSH 连接、Agent 部署、环境握手、远端文件与终端、远程 LSP 启动。先验证远端 C/C++，再验证 Rust 和 Python。

验收：在远端文件中完成打开、修改、保存、补全、诊断和定义跳转；日志证明服务器运行在远端。测试同路径多主机隔离、主机密钥错误、Agent 版本冲突、断线重连和保存冲突。

### 阶段 D：统一任务与实验结果接入

从 Python 脚本运行和独立 CMake 插件入手，建立统一的任务执行、输出与取消流程，再扩展 Cargo 构建/测试和格式化命令。接入产物选择、结果保存和论文工作区使用，沿用核心的结果记录。

验收：本地与远端任务在正确环境执行，取消与失败状态真实可见；构建目标和输出可追踪；完成第 9.1 节的研究流程。远程产物传输失败不得显示保存成功，结果能回到对应运行记录，并明确代码版本信息的缺失或工作区修改状态。

### 阶段 E：工具自动安装与资源扩展完善

逐工具增加受支持平台的下载安装与回退。迁移六套主题，保留主题标识和强调色偏好；后续根据使用需求决定主题导入和论文模板扩展。

验收：安装取消和失败不破坏旧版本；本地/远端安装位置正确；不支持的平台给出明确结果。旧主题偏好保持，深浅主题下实际界面可读，切换和失败回退正常。

主题迁移可以在阶段 A 后穿插进行，不是阶段 B、C、D 的前置条件。阶段 C、D 可先使用已有工具完成验收，自动安装不作为远程连接和实验流程的前置条件。

## 11. 验证策略

测试重点放在公共边界和真实功能，避免只验证 Manifest 能被读取：

| 层级           | 关键验证                                                                                 |
| -------------- | ---------------------------------------------------------------------------------------- |
| 注册与生命周期 | 重复 ID/贡献、不兼容接口、激活失败清理、工作区覆盖、停用释放；引入依赖机制后补充依赖校验 |
| 环境接口       | Windows/POSIX 路径、参数转义、取消、输出限额、跨环境身份隔离                             |
| 语言服务       | 使用实际服务器完成补全、诊断、跳转，验证服务崩溃与重启                                   |
| SSH            | 在可复现 Linux SSH 环境验证部署、握手、读写、终端、断线与重连                            |
| 任务与结果     | 正确执行环境、取消与退出状态、产物选择、传输完整性、保存失败、来源关联与论文工作区使用   |
| 工具安装       | 校验失败、取消、无网络、架构不支持、旧版本保留                                           |
| 主题与页面     | 运行中的桌面应用检查主题切换、状态文案、对比度及失败回退                                 |

现有 LSP 与编辑器测试继续作为回归基础。模拟环境用于失败注入，不能替代真实 SSH 与真实语言服务器验收。

每个实现提交遵守仓库要求，运行 `npm run ci:check` 并确认输出 `CI checks passed.`。本文只定义设计，不代表上述验证已经执行或能力已经交付。

## 12. 后续需落实的工程决策

以下项目必须在对应阶段进入实现前明确；其中设置迁移在阶段 A 落实，其余不作为阶段 A 的前置条件：

1. Agent 打包方式、最低 Linux 系统要求、支持的架构和发行渠道。
2. SSH 交互认证、配置选项和跳板机的实际支持矩阵。
3. 每个工具的可分发平台、版本策略、许可证及安装来源。
4. 设置持久化与现有偏好存储的迁移细节。
5. 第三方插件开放条件；需要时另写隔离、权限和版本兼容设计。
6. 阶段 D 的任务贡献接口、现有实验结果模型的复用方式，以及远程产物传输、保存位置和来源记录的具体约定。
